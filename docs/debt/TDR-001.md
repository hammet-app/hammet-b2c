# TDR-001 — Deferred B2C Implementation Functionality

**Category:** Architecture  
**Status:** Deferred  
**Priority:** Medium  
**Owner:** Frontend  
**Review Date:** 2026-11-13

## Context

The current B2C implementation prioritizes the functionality required for the initial rollout over more comprehensive cart management, synchronization, and support workflows.

Three areas have been deliberately simplified or deferred.

---

## Debt 1: No Clear Cart Function

**Current State:**  
The cart does not have a dedicated clear function. Items must be removed manually.

**Why Deferred:**  
The current implementation prioritizes the core purchasing functionality required for the initial rollout.

**Decision:**  
Leave the cart without a clear function for now.

**Fix Trigger:**
- Users need a convenient way to empty their carts.
- Cart management becomes a more prominent part of the purchasing experience.
- The cart implementation is revisited for broader improvements.

---

## Debt 2: No Dexie-to-Backend Cart Synchronization

**Current State:**  
The cart is stored locally in Dexie (IndexedDB), but synchronization from Dexie to the backend has not been implemented.

**Why Deferred:**  
The immediate focus is on supporting the purchasing functions required for the initial rollout. Given the expectation that a user will most likely be purchasing a course for one school at a time, implementing a complete synchronization flow is not currently a priority.

**Decision:**  
Keep the current local cart implementation and defer Dexie-to-backend synchronization until product requirements justify it.

**Fix Trigger:**
- Users need to resume carts across devices or browsers.
- Backend-side cart management becomes necessary for the purchasing flow.
- The local-only approach creates measurable usability or reliability problems.

---

## Debt 3: Simplified Support Workflow

**Current State:**  
Support functionality is being scaled back from a comprehensive, website-based support experience to a simpler workflow in which users send support requests by email.

**Why Deferred:**  
Building a complete support system within the website would add implementation work that is not essential to the current rollout.

**Decision:**  
Use email as the primary support channel for now, rather than building the full support workflow into the website.

**Fix Trigger:**
- Support volume becomes difficult to manage through email.
- Support requests require structured tracking, assignment, or status management.
- Users need to follow the progress of their support requests within the platform.
- Operational requirements justify a dedicated support interface.

---

## Consequences

**Accepted for now:**
- Cart items must be removed individually.
- Cart state is not synchronized from Dexie to the backend.
- Support requests are handled through email rather than a comprehensive in-platform workflow.

**Expected benefits:**
- Reduced implementation complexity.
- Faster delivery of the core B2C purchasing experience.
- Engineering effort remains focused on the functionality required for the initial rollout.

## Review Notes

At the review date, reassess each item against actual user behavior, purchasing requirements, and support volume.

These debts should be evaluated independently. One may become necessary to resolve before the others.
